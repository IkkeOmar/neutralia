NEUTRALIA — technical stack decision

All version numbers and sizes verified against live sources 2026-11-08. Sources are listed inline. Anything not verified is marked UNVERIFIED.

0. What we learned from the site Omar pointed at

Omar's instruction (2026-11-08): "you should definitely learn from the website that I reference to you earlier". The earlier research in this project had searched Ported2Browser and wasm.rip, so those are the references.

wasm.rip — "a group of people on the internet, porting games". Their ports are mostly recompilations: existing C/C++ or C# code translated and compiled to WebAssembly via Emscripten, with WebGPU where it helps. The directory lists real multiplayer browser ports, including Counter-Strike Surf, a browser-native Source-engine recreation with online ranked and unranked runs and Source-style physics at 66 tick.

ported2browser.net (the research table for the directory) — 305 ports as of 4 Nov 2026; 26 documented in detail. The methods cluster into four buckets: recompile-to-WASM (Emscripten), decompilation projects (re3, reVC), emulator-in-page (DOS/PS2/PSP), and new-engine recreations. Multiplayer appears in: Counter-Strike Surf (ranked servers, 66 tick), GTA V (sandbox), NFS Most Wanted (online free roam, ranked + casual races), SOCOM II (online multiplayer + voice), FIFA Street 2 (experimental online), DBZ Budokai 3 (experimental online 2P).

The three lessons that actually transfer to us:

  1. Native WASM in the browser is a solved delivery mechanism. Every working port ships as WASM in a tab. The failure mode of the original is precisely what we must avoid: Battlefield Heroes needed a downloadable plugin, and Chrome began pulling NPAPI support in 2014, which killed the delivery mechanism while the game was still running on it. rip.so's obit for BFH names this explicitly. We ship no plugin. Everything is standard browser APIs.
  2. Tick rate is the multiplayer contract. Counter-Strike Surf runs 66 tick with ranked servers in a browser. Our server runs 30 Hz simulation with 60 Hz physics substeps — comparable, and measured against a genre that has a decade of netcode tuning behind it.
  3. The Emscripten route does not apply to us. The dominant porting pattern is "compile existing C/C++ to WASM", which only makes sense because those projects have pre-existing codebases. NEUTRALIA is an original game with no code to compile. The transferable half is the architecture — WASM-ready, no plugin, single origin, static delivery.

Bundle-size comparison from the same sources — this is the decisive argument for the stack:

Delivery Engine payload Note
Three.js custom stack ~138 KB gzip (measured — our own build) renderer + game code
Godot Web export ~5 MB Brotli empty
Unity WebGL ~7.7–10.7 MB Unity 6.6 lifts the WASM memory ceiling to 16 GB with Wasm64
BFH (2009) "sub-250MB download" plugin-based

BFH's own 2009 budget was ~250 MB. Our entire engine is 138 KB gzipped — smaller than a single BFH character texture. That is the "lightweight" requirement met with three orders of magnitude to spare, and it is why we do not need Unity's asset pipeline or its WASM memory ceiling.

1. Renderer — Three.js 0.187.0, WebGL2 first

Decision: Three.js 0.187.0, starting on WebGLRenderer. WebGPURenderer is a later opt-in, not a dependency.

Verified (2026-11-08): npm three@0.187.0 (r187). Bundle: 725 KB raw / 181 KB gzip (bundlephobia). Babylon.js 9.35.0: 8.1 MB / 1.8 MB gzip. PlayCanvas 2.23.3: 2.4 MB / 622 KB gzip. Our actual Vite build measured 132.9 KB gzip for the Three chunk plus 4.5 KB app code — smaller than bundlephobia's figure because Vite tree-shakes.

Why Three.js and not the alternatives:

  • Byte cost is decisive. 181 KB vs 1.8 MB vs 622 KB. Against a "well under 50 MB" target all three fit, but the engine should not be the budget.
  • WebGL2 is the correct default for a low-end target. WebGPU's wins are compute shaders and lower CPU draw-call overhead. A 16-player scene with ~100 draw calls is not CPU-bound. WebGPU matters more on mobile than on the desktop iGPU target.
  • WebGPU's fallback story is good but its maturity is not. Three.js's own manual still calls WebGPURenderer experimental, and it does not support ShaderMaterial / RawShaderMaterial / onBeforeCompile — custom GLSL would need porting to TSL. Babylon's WebGPU is production-grade; if we need compute shaders later, Babylon is the fallback.
  • 2026 landscape: Safari 26 (Sept 2025) enabled WebGPU by default; Firefox still ships it disabled by default in stable. Global support ~87–89%. WebGL2 fallback is mandatory, not optional — which the Three.js WebGPURenderer gives us for free at init with no dual codebase.

Fallback stack: Babylon.js 9.35 + Havok (@babylonjs/havok@1.3.14) if writing glue over Three.js proves painful. Costs ~1.8 MB gzip engine + 2.09 MB havok.wasm.

2. Physics — Rapier 3D 0.21.0, deterministic build on the server

Decision: @dimforge/rapier3d 0.21.0. Server uses the deterministic build; client uses -compat (base64-inlined WASM, no bundler fights).

Verified (2026-11-08): npm @dimforge/rapier3d@0.21.0. External WASM build 2.94 MB; -compat 4.2 MB minified JS / 1.6 MB gzip. cannon-es@0.20.0 is 120 KB / 34 KB gzip. ammo.js@0.0.10 is effectively frozen (last real work ~2019). Havok's WASM is 2,094,566 bytes.

Why Rapier and not cannon-es despite the size: the deterministic build is the only one of the four that guarantees bit-identical simulation across machines. That is exactly what lockstep prediction/reconciliation depends on. A 34 KB engine that diverges by one float between server and client produces a rubber-banding bug that is expensive to diagnose later. Rapier is also the only one with a maintained character-controller and raycast API.

What a third-person shooter with vehicles actually needs is narrower than a full rigid-body engine: raycasts for hitscan, a capsule character controller, and vehicles as kinematic bodies the server integrates. Rapier's raycasts and kinematic bodies are its sweet spot; we do not need the full dynamic pipeline.

Already done: the current slice ships its own compact kinematic solver in shared/movement.js — one implementation imported by both client and server, so client prediction and server authority can never diverge. The test asserts bit-identical agreement between two independent runs. Rapier replaces the collision layer (capsule vs. world, step height, slopes) while the kinematic controller logic stays ours.

3. Netcode — Colyseus 0.18 for the authoritative server

Decision: colyseus@0.18.12 server + colyseus.js client.

Verified (2026-11-08): npm colyseus@0.18.12. Client bundle 227 KB / 61 KB gzip.

Colyseus 0.18 is the only option where client-side prediction, reconciliation, and server-side lag compensation are already built and documented for exactly this genre: setFixedTimestep(), allowRewindState({maxRewindMs}), and subSteps to run 60 Hz physics under a 30 Hz network tick. That combination was previously hand-rolled in every browser shooter.

Rejected alternatives: Rivalis@8.0.0 has no prediction or lag compensation (you would hand-roll the shooter-critical parts). murow@0.4.1 is promising but a very young single-maintainer project (created Dec 2025). @web-engine-dev/* is not on npm — its docs describe a full ECS engine with GGPO rollback, but npm install 404s. Do not build on it.

Rates for 12–16 players with hitscan guns:

Value Why
Server simulation tick 30 Hz matches the browser-port precedent (CS Surf runs 66 tick with ranked servers)
Physics substeps 2 → 60 Hz stable movement and vehicles under a 30 Hz network tick
Snapshot rate to clients 15–20 Hz delta-compressed; ~a few KB/player/s
Client prediction 30 Hz local player responsive with no visible rubber-band
Remote interpolation ~100 ms in the past smooth remote motion
Hitscan server-side lag compensation, rewind up to 250 ms "what you see is what you hit"

Transport: WebSocket now, WebTransport later. WebTransport became Baseline when Safari 26.4 shipped it (March 2026), and an NSDI 2025 study measured it beating WebSockets under packet loss (unreliable datagrams avoid TCP head-of-line blocking). But QUIC runs over UDP, which some corporate and school networks block — so a WebSocket fallback stays mandatory. WebTransport is an optimisation to add after the slice, not a dependency of it.

Already done: the slice implements the same architecture by hand — server owns positions, health and hit detection; the client sends intent only; the server rejects a client that tries to inject a position (asserted by the test); the client predicts locally and reconciles against the server snapshot. Colyseus replaces the hand-rolled transport and adds the lag compensation we have not hand-built yet.

4. Asset pipeline — Meshopt + KTX2/ETC1S

Decision: glTF 2.0 with EXT_meshopt_compression + KTX2 (ETC1S for colour, UASTC for normal/ORM) + WebP for non-PBR textures. Tooling: @gltf-transform/cli + gltfpack.

Draco Meshopt
Extension KHR_draco_mesh_compression EXT_meshopt_compression
Compresses triangle meshes only — animation and morph targets pass through vertices, indices, morph targets and animation keyframes
Decoder 192–286 KB WASM + 58 KB wrapper 32 KB JS module (inline WASM)
Decode speed considerably slower ~1 GB/s (WASM SIMD)

Meshopt, because our characters are animated. Draco does not compress animation tracks, and for a soldier with an animation set the animation is often the largest single component — Draco would leave most of the bytes on the table.

Texture budget (2048×2048 with mipmaps): RGBA8 ~22 MB → UASTC ~5.6 MB → ETC1S ~2.8 MB. ETC1S is ~0.3–3 bits/pixel on disk and transcodes to GPU block format, so it stays compressed in VRAM (4–8× less GPU memory — the biggest single lever on a 4 GB machine).

Realistic first-load budget for a BFH-class stylised scene (grey-box + one soldier + one rifle + one vehicle, Meshopt + ETC1S + WebP, Brotli): 5–12 MB, map streamed in tiers. Rule of thumb from the 2026 sources: first scene under ~10 MB on the wire, VRAM under 150–200 MB, hero character 30–50k triangles, props under 5k.

5. Hosting — GitHub Pages for the app, Cloudflare R2 for assets

Decision: app on GitHub Pages, large binaries on Cloudflare R2, game server on the VPS.

Origin Per-file limit CORS COOP/COEP
GitHub Pages 100 MB serves Access-Control-Allow-Origin: * (verified by curl) cannot set
Cloudflare Pages 25 MB configurable configurable
Cloudflare R2 ~5 TB/object configurable n/a
jsDelivr 20 MB (GitHub files) yes n/a
GitHub Releases 2 GB no CORS on the asset CDN → browser fetch() fails n/a

The COEP trap is avoidable by stack choice, not by header gymnastics. Threaded WASM builds need SharedArrayBuffer, which needs COOP/COEP, which GitHub Pages cannot set. Our stack is single-threaded — Rapier and Colyseus run single-threaded, Three.js renders on the main thread — so we dodge COOP/COEP entirely and GitHub Pages works with zero header hacks. (If threads are ever wanted: coi-serviceworker shims it, or move to Cloudflare Pages which can set the headers.)

R2 wins for assets: free egress (a 20 TB month of downloads costs $0), 10 GB free storage covers an entire asset set, and we control CORS/CORP.

Reject GitHub Releases for runtime asset loading — no CORS headers on the actual file, so fetch() fails. Fine as a human-downloadable distribution archive. Reject jsDelivr for scene files — 20 MB per-file cap, plus third-party dependency.

What the slice proves, concretely:

  • The server owns positions. A client that injects a position field is ignored.
  • Movement propagates: client A's input moves A on the server; client B sees it.
  • Hitscan is server-validated. The client sends a ray; the server raycasts the world, finds the nearest target, applies damage, and broadcasts the shot.
  • Fire rate is server-enforced (burst of 10 in 100 ms → 3 shot events).
  • Death and respawn work; the victim returns to a spawn point.
  • The shared movement module is bit-identical between two independent runs — that is what makes prediction safe.
  • The client predicts locally and reconciles against the server snapshot.

7. Next steps, in order

  1. Rapier for collision — capsule character controller, step height, slopes. The kinematic movement logic stays ours; Rapier owns the collision queries.
  2. Colyseus for the transport — replaces the hand-rolled WebSocket protocol, and adds lag compensation (allowRewindState) that we have not hand-built.
  3. A real map — glTF grey-box from a Blender export, Meshopt-compressed.
  4. A soldier model with animation, Meshopt + ETC1S, streamed.
  5. A weapon — hitscan ray already works; add a projectile weapon to exercise the non-hitscan path.
  6. Vehicles — kinematic bodies with a vehicle controller, per the chassis × variant system in systems/vehicle-system.md.
  7. Deploy — app to GitHub Pages, assets to R2, server to the VPS behind a subdomain with a WebSocket route.
