1 — What a skill actually is

A skill is a Markdown file with instructions that get loaded into the agent's context when relevant. It is not a program, not a library, and it does not run by itself. It is a written-down set of decisions so that the same mistake is never made twice, and so that the reasoning survives even if the conversation does not.

The quick-tunnel trap, because it cost real time

cloudflared tunnel --url silently loads ~/.cloudflared/config.yml. That file contained a catch-all ingress rule ending in http_status:404 — so every single request through the tunnel returned a 404, including the WebSocket upgrade. The tunnel was not broken; it was faithfully obeying a stale config.

The fix is a one-line explicit config with nothing in it: cloudflared tunnel --config /tmp/quick-empty.yml --url http://127.0.0.1:8800, where the file contains just tunnel: quick. That lesson is now written into the hosting skill so it cannot bite again.

3 — Ten bugs, written down so they cannot recur

None of these were found by reading the code. Every one was caught by a test that asserted a specific physical or network property and failed. This is the actual value of the skill: it is a list of traps that have already been sprung.

01A kinematic body only moves when the world steps

The character-movement function returned body.translation() + computedMovement — the target position — while the caller also stepped the physics world. The logical state and the physics body therefore disagreed by the collision margin, every single step.

The symptom was subtle and maddening: the player would walk normally for a couple of seconds and then stop dead against a wall, with the code insisting they were still moving. The two representations were fighting, and the reconciliation logic snapped the player back to the wall on every snapshot.

Rule The movement function steps the physics world itself and returns the body's real post-step translation. The caller must never step again. One call equals one authoritative step.
02The static raycast was hitting players too

Hitscan resolves in two parts: cast against the static world, cast against character capsules, then take whichever hit is closer. The static cast was not excluding character capsules, so it stopped at the player too — and since the two distances were computed identically, the character hit was never strictly closer.

Net effect: nobody could ever be shot. The game looked alive and functioned perfectly. It simply could not register a hit.

Rule The static raycast excludes every character collider via the filter predicate — which is the eighth argument of Rapier's castRayAndGetNormal, not the one people usually reach for. The character cast does the exact opposite and matches only its target.
03Shots passed 0.9 m over everyone's head

The game works in "feet space" — a player's position is where their boots touch the floor. Rapier's capsule, however, is centred on the body. A ray origin was being converted from feet space into centre space, which lifted the muzzle by exactly half the player's height.

Every shot sailed 90 cm over the target's head. Aiming down at a target's chest missed them entirely.

Rule Hitscan muzzle positions are absolute world positions. The feet-space to centre-space conversion applies only to character body positions, never to ray origins.
04The client predicted at half the server's rate

The server ran two physics sub-steps per 30 Hz network tick — 60 Hz simulation. The client predicted at 30 Hz. So the client's position ran ahead of the authority, and every authoritative snapshot yanked the player backwards by the difference.

The fix was to move the sub-step constants into the shared protocol module so both sides import the same numbers, and to have the client predict at the physics rate rather than the network rate.

Rule The simulation rate lives in shared/protocol.js and both sides import it. The client predicts at SUB_DT and emits one input per sub-step.
05The input buffer starved and the player stopped walking

The server originally took the newest input and applied it to both of its sub-steps, so the authority advanced twice for every single input the client sent. On top of that, the client batched its inputs on a requestAnimationFrame timer, so the batch size oscillated between one and three depending on frame timing.

When a batch happened to contain only one input, the server ran out and fell back to repeating a stale one. The player's effective input rate fell below the simulation rate. The visible symptom: the player moved 2.6 metres and then stopped dead, still holding the key.

Rule The server keeps an ordered input buffer and consumes exactly one input per sub-step, oldest first. The snapshot reports the last input actually simulated (consumedSeq), not the last one received — reporting the received number tells the client to discard inputs the server has not run yet.
06Reconciliation forgot the velocity and the body

When an authoritative snapshot arrived, the client snapped its position to the server's and replayed the unacknowledged inputs on top. But it never restored the authoritative velocity, and never told the physics engine where the body had been moved to. The next movement query therefore resolved against a stale transform.

Rule Reconciliation resets three things together: the position, the velocity, and the physics body's transform. Then, and only then, replay the unacknowledged inputs.
07An explosion was pushing the feet, not the body

The blast direction was computed from the target's feet position to the explosion. A rocket detonating at ground level under a standing player is 90 cm below that player's centre of mass — so the push was almost horizontal, and the rocket jump simply did not happen. The player got shoved sideways.

This is the single most important line in the whole explosion model, and it is the reason the jump is physical rather than scripted. More detail in section 4.

Rule The blast pushes the body's centre of mass. When the body is standing on a surface, any downward component is converted into an upward bounce, because a surface cannot be pushed through — the energy goes up instead.
08Every cloned soldier shared one skeleton

Three.js' ordinary Object3D.clone() copies a Skeleton by reference. Every spawned soldier was therefore bound to the original model's bones — they would all animate as one figure, and the clones would render against the wrong rig.

Rule Any glTF scene containing a skinned mesh must be duplicated with SkeletonUtils.clone() from three/addons/utils/SkeletonUtils.js. Never Object3D.clone().
09The assets were in a folder the bundler never looked at

The glTF files were written to engine/assets/. The bundler's root is engine/client/, so those files were never copied into the build output. The fetches 404'd and the client silently fell back to primitive boxes and capsules — with no error in the console beyond a warning nobody read.

Rule Assets live in client/public/assets/, which the bundler copies verbatim. The asset build script writes there directly, so there is no copy step to forget and no way for the two locations to drift apart.
10The camera was the aim source, and it points at the player

Firing took its direction from the camera's forward vector. But a third-person camera always looks at the character, so its forward vector always pointed at their chest. A rocket aimed at the ground hit the shooter's own torso.

The crosshair had the same problem for the same reason: it marked a direction the shot did not follow.

Rule Derive the aim vector from the player's yaw and pitch, and point the camera along that vector so the crosshair and the shot agree. The pitch convention in this engine is positive = looking up.

4 — The rocket jump, explained physically

The brief was specific: reproduce the Battlefield Heroes behaviour where detonating a rocket at your own feet launches you absurdly high. This is how it was modelled — and why the centre-of-mass detail above is the whole trick.

The explosion sits below the centre of mass, so the push points up. Measured from the feet, the same blast points sideways and the jump never happens.

Three rules make it work, and all three are sourced rather than invented:

  • Self-splash Quake II's rule: your own blast deals half damage but pushes at 1600/mass instead of 500/mass — a factor of 3.2.
  • Explosive strength DICE's Refractor 2 engine exposes a ForceOnExplosion property on a 0–50 scale: explosive packs 50, landmines 30, Katyushas 15, grenades 10, bazookas 2.
  • The ground bounces you a surface cannot be pushed through, so any downward component of the blast is redirected upward.

The falloff curve also needed correcting. Quadratic falloff crushed the near field: a rocket 60 cm under your feet got 25% of the push while one at zero got 100%, so the same weapon felt like it either did nothing or launched you into orbit. A t^1.5 curve keeps the falloff physical while leaving the near field usable, which is the entire point of a rocket jump.

WeaponApexBehaviour against infantry, and why
Panzerfaust (rocket)~9.7 mStrong. The community-documented "Roquet-Jump" weapon.
Sticky TNT~14 mWeak against players, devastating against vehicles. The BFH community guide calls it "très faible contre les joueurs" — it behaves like a vehicle against a vehicle.
M32 MGL~4 mLethal to infantry at point blank, very weak against vehicles.

The map's walls are 8 m and its towers 3.6 m, so a rocket jump at 9.7 m clears the walls comfortably and lands you on top of most structures — the intended tactical use.

5 — The test suite and what it proves

98 checks across five suites. The browser tests assert the player's actual physical state, not that a page loaded — a screenshot on its own is not a test.

  • Explosion physics — 20 checks node test/explosions.js
    Blast geometry, self-push ratio, self-damage halving, mass behaviour, falloff, and the requirement that the standard and deterministic physics builds produce a bit-identical apex. This is the suite that proves the rocket jump is real.
  • Integration — 29 checks node test/slice.js
    The authoritative server end to end: joining, movement, hitscan damage, and disconnect handling.
  • Assets — 16 checks node tools/verify-assets.mjs
    Both GLBs decode with the standard loader, the map's 16 nodes match the shared map definition exactly, the soldier has a bound skeleton with 19 bones, correct joint and weight attributes, and two animation clips that actually deform the rig.
  • Browser — 16 checks node test/browser.cjs $URL
    WebGL context alive, the canvas contains rendered geometry rather than a background, the HUD is wired, and the player actually moves when a key is held.
  • Rocket jump — 17 checks node test/browser-rocket.cjs $URL
    The whole chain in a real browser: the model is skinned with 19 bones, the rocket is fired at the player's own feet, the player leaves the ground, reaches a useful height, comes back down, and lands on the floor rather than through it.

    • Two lessons from the test harness itself

    Poll for assets, do not sample once. The 4.3 MB physics WASM has to download and parse before the client can even boot, and the models load after that. A test that checked once reported a false failure — the asset was two seconds away.

    Expose a read-only debug surface. Module-scoped variables are unreachable from a browser test, so the client publishes a small window.__NEUTRALIA object with getters. Adding a getter there is much cleaner than reaching into module scope from outside.
